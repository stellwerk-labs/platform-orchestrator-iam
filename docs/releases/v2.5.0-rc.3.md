# IAM v2.5.0-rc.3

This release candidate adds plugin capabilities, short-lived plugin workload
identity and the permissions used by the deployment queue and Plugin Manager.
Use it to test the coordinated release candidate, not as a stable production
release. The plugin contract is `v1alpha`, limited to first-party plugins. It is
not a stable partner SDK or a sandbox for untrusted plugin code.

## Since rc.2

Publication evidence now binds a manually dispatched candidate to its actual
branch and workflow. The previous candidate passed all product tests but was
stopped before image publication by a check that only accepted `main`. Stable
releases remain restricted to pushes on `main`; candidate branch access still
requires the protected environment's review. Application code, migrations and
the published Go module are unchanged.

## What changes

- Organisation-scoped plugin capabilities can be registered through
  `/orgs/{orgId}/plugins/{pluginId}/capabilities`. Permission checks accept
  complete capability IDs. A plugin capability never grants an Orchestrator
  permission.
- `/auth/plugin-workload-token` exchanges a projected Kubernetes ServiceAccount
  token for a short-lived, audience-bound plugin token. The default lifetime is
  15 minutes, configured with `PLUGIN_WORKLOAD_TOKEN_TTL`. Workload bindings tie
  the plugin and installation IDs to a ServiceAccount, namespace and principal.
- Platform principals are service users with `scope: platform`: they belong to
  no organisation and cannot hold roles. A workload principal has no static
  token. Create its binding with `platform_principal: {display_name}`, or name
  an existing unbound workload principal with `service_user_id`. Revoking a
  binding removes its issued tokens but retains the principal for rebinding.
- A bound service user that holds or gains a role cannot exchange or use
  workload tokens. Assigning a role to a bound service user returns 409.
- `/platform-principals` manages static-token platform principals, including the
  Data Plane admission checker. Creating or regenerating a static token requires
  a human user or IAM's internal system identity. Replaced or deleted static
  tokens stop authenticating within the 60-second authentication cache window.
  IAM logs principal and binding changes with the operator's identity.
- `deployment.outcome.acknowledge` is a manage permission for acknowledging
  deployment outcomes, grantable at organisation, Project or Environment scope.
  Legacy `manage_all` also grants it.
- `plugin_manager_read` and `plugin_manager_write` are platform permissions for
  human users listed in `PLUGIN_MANAGER_READERS` and `PLUGIN_MANAGER_WRITERS`.
  Organisation roles do not grant them, and service users cannot hold them.
- Authorization now checks identity liveness before consulting a cached policy.
  Deleted users and service users without a current, unexpired token no longer
  remain authorised through a cached policy.

## Administrator actions

Plugin management is opt-in. Set `PLUGIN_MANAGER_WRITERS` before operating the
Plugin Manager; an unset value grants nobody write access. Configure workload
verification with `PLUGIN_WORKLOAD_TOKEN_ISSUER`, `PLUGIN_WORKLOAD_JWKS_*` and
`PLUGIN_WORKLOAD_BINDING_WRITERS` when enabling plugins. The Orchestrator, not
the workload principal, registers capabilities for each enabled organisation.

The Control Plane and Data Plane require the admission checker to be a
static-token platform principal. An organisation service user is not a valid
replacement. See
[workload identity and platform principals](../plugin-workload-identity.md) for
creation, rotation and binding instructions.

Review automation that relied on a deleted principal still passing checks. Grant
`deployment.outcome.acknowledge` only to operators allowed to clear an
unreconciled Environment after reviewing its deployment outcome.

## Upgrade and recovery

Migrations 36 to 38 add capability and workload identity tables and platform
principal constraints. Migration 38 adds the service-user scope column, changes
nullability under a check constraint and replaces the role foreign key. Existing
organisation service users retain their organisation, token and expiry.

IAM 2.4.0 cannot start on schema 38, because its latest migration is 35. Do not
roll back to that image after upgrading. The coordinated chart uses the
`Recreate` strategy for IAM. Recovery must retain schema-compatible IAM
binaries; an application configuration rollback is not a database downgrade.

If a pre-release installation has a workload binding to an organisation service
user (`service_user_scope: organization`), replace it with a platform principal.
Revoke the old binding, create a new one with `platform_principal`, then record
the new principal in the Plugin Manager with
`octl plugin-manager create-identities`. Legacy bindings work only while the
organisation service user holds no role. IAM creates no new bindings of that
kind.

## Go contract and compatible set

The published `shared/v1.2.0` module at
`github.com/stellwerk-labs/platform-orchestrator-iam/shared` adds platform
permissions, `PlatformCheck`, binding lookup and platform-principal clients,
including `PluginWorkloadBinding.service_user_scope`. It requires Go 1.26.2;
published enum names are unchanged. The application candidate does not retag the
shared module.

Test with CP 3.1.0-rc.1, DP 4.0.0-rc.1, Console 1.4.0-rc.1, CLI and
Terraform/OpenTofu provider 2.1.0-rc.1, and chart 0.8.0-rc.1. These versions
name the coordinated candidate set, not a claim that every component is already
published or qualified.
